# Миграция схемы

`DatabaseManager` намеренно не включает `eraseDatabaseOnSchemaChange`:
для клиента мессенджера молчаливое удаление локальной истории при
изменении схемы — плохой сюрприз. Каждая правка таблиц идёт отдельной
миграцией.

## Правила

1. **Новая колонка** — отдельная миграция `vN` с `ALTER TABLE ... ADD COLUMN`
   и значением по умолчанию.
2. **Изменение типа или переименование** — копирование в новую таблицу
   внутри транзакции миграции (`CREATE TABLE ... AS SELECT`), затем
   `DROP`/`RENAME`.
3. **Имя миграции** не меняется после релиза: GRDB отслеживает
   применённые миграции именно по имени.
4. **Тесты** прогоняют миграции на in-memory базе
   (`Tests/CoreTests.swift` → `RepositoryTests`). Если миграция не
   применяется к коду репозиториев, тест падает сразу.

## Что происходит на устройстве

При первом запуске новой версии GRDB применит недостающие миграции
к `Application Support/max-client.sqlite`. Историю сообщений это не
затрагивает. Если миграция падает, приложение упадёт на
`DatabaseManager.makeQueue()` — исправлять нужно миграцией, а не
чисткой базы пользователя.
